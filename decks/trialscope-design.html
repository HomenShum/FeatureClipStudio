TrialScope

The demo worked. Then it met production.

Six things I believed while building this. Each one was measured. Each one was wrong.

What a demo assumes

One user. A warm cache. The API always answers. The numbers add up. The tests mean the code runs.

What actually happened

Many tenants on one budget. Cold starts. Bursts that collapse. Buckets that overlap. A module nothing ever called.

6 beliefs, each killed by a number — every figure in this deck is from MEASUREMENTS.md
Failure 1 · the model does arithmetic

A model that adds up is a model that makes things up.

The easy way

Pull a page of studies, group them in code, let the model summarise the totals.

What it costs you

Every number becomes unverifiable. Nobody can tell a real count from a plausible one.

question→ plan the buckets→ one count probe each→ chart ·sum client-side
37 probes behind one network graph — each keeps its URL, and re-issuing it returns the same count
Failure 2 · the buckets lie

The totals matched. The buckets still overlapped.

A trial can be Phase 2 and Phase 3. I checked the sum against the total and called that proof.

Failure 3 · one budget, many tenants

Jitter felt like the fix. It measured like nothing.

Fairness across tenants sharing one upstream budget. Jain index — 1.0 is perfectly fair.

Tried first — randomised backoff

0.139 → 0.150

Spreading collisions in time does not decide who goes next.

What worked — FIFO arrival order

→ 0.986

Fairness is a queueing property, not a timing one.

0 tenants a share cap can save on its own — max_tenant_share bounds work in flight, and a tenant that grabs and releases instantly never touches it
Failure 4 · the cache leaks

A shared cache tells one tenant what another asked.

The assumption

A cache is a performance detail. Tenants share it, results are public data anyway.

The measurement

Hit and miss are distinguishable by clock. That difference is a channel.

31,377× timing gap between a cached and an uncached answer — closed by giving every tenant its own cache over a shared, FIFO-ordered quota
Failure 5 · the herd

Eight identical questions should cost one answer.

8 concurrent asks→ single-flight→ 1 upstream request
8 → 1 and the trap: a synchronous mock hides this entirely. Under a fake transport the calls collapse anyway and the bug reports itself as already fixed. The test needs a transport that really awaits.
596,902 vs 2,917 what the same cache returns when the key is wrong — "counts are identical" was in the README before anyone measured it
Failure 6 · the worst one

Correct, tested, documented — and never called.

Every signal was green

Passing tests. A README section. A measured 31,377× channel it closed.

Nothing constructed it

The module was unreachable from the running service. Tests passing is not the same as code running.

0 callers — the rule this forced: a surface with no screenshot has not been checked, however green its tests are. Two user-visible defects were found only by asking for a capture that did not exist.
